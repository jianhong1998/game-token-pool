Tooling swap: npm → pnpm, GNU Make → just

Six commits swap the repo's package manager (npm → pnpm) and task runner (GNU Make → just) across the app, Docker, CI, and docs, with an explicit constraint of zero behavior change to the Solana program or web app. The lockfile was migrated (not regenerated) to avoid dependency drift, and every make target got a 1:1 just recipe with dash-renamed names.

Why

This is a pure tooling-preference change, not a fix for anything broken — npm and make both worked fine before. The repo already has a strong convention of pinning toolchain versions exactly (Anchor 1.1.2, Solana CLI 3.1.10, surfpool 1.5.0) to avoid silent drift; that same philosophy drove the two riskiest choices here: generating pnpm-lock.yaml via pnpm import from the existing package-lock.json (preserving already-resolved versions) instead of a fresh pnpm install (which could re-resolve transitive deps within the same semver ranges), and pinning packageManager: "pnpm@9.15.3" exactly rather than a floating range.

Because docs (README.md, CLAUDE.md) and Docker/CI both reference package-manager and task-runner commands, the plan intentionally landed both halves of the swap together rather than splitting pnpm and just into separate change sets — splitting them would have meant touching the same doc files twice for no benefit.

Package manager migration: npm → pnpm (lockfile, package.json)

Commit 7b1e395 is the foundation everything else depends on. pnpm import reads the existing package-lock.json and writes pnpm-lock.yaml with the same already-resolved dependency versions, rather than letting pnpm's resolver pick fresh versions within the same semver ranges — the review confirmed all 29 direct dependencies resolved identically, with the only lockfile diff being the metadata change from moving overrides to pnpm.overrides (pnpm doesn't read a root-level overrides key, so leaving it in place would have silently stopped pinning postcss to ^8.5.10). package.json also gained "packageManager": "pnpm@9.15.3", pinned exactly rather than as a range, matching the repo's existing toolchain-pinning convention — this also lets pnpm/action-setup@v4 in CI read the version without a separate pin, so packageManager stays the single source of truth. package-lock.json was deleted in the same commit as a hard cutover.

To avoid dependency drift — a fresh `pnpm install` could re-resolve transitive dependencies to different versions within the same semver ranges, which conflicts with the repo's practice of pinning toolchain/dependency versions exactly.

To match the repo's existing convention of pinning toolchain versions exactly (Anchor 1.1.2, Solana CLI 3.1.10, surfpool 1.5.0), and so `pnpm/action-setup@v4` in CI can read that exact version with no separate `version:` input.

Task runner migration: GNU Make → just

Commit 31b13bc replaces makefile with a new root justfile in one change (no transition period — both files never coexist in the committed history). The justfile mirrors the makefile's 16 targets 1:1, flat, with no just modules or [group(...)] tags (judged unnecessary structure for 16 recipes that already read fine alphabetically). Because just recipe names can't contain /, every slash-style Make target was renamed with dashes — up/build → up-build, solana/set/dev → solana-set-dev, deploy/with-airdrop → deploy-with-airdrop, etc. Recursive $(MAKE) target calls became just target calls, which just supports natively. One deliberate non-fix: the original makefile's PROJECT_DEPLOY_KEY="~/.config/solana/devnet-id.json" had embedded literal quote characters that end up in the expanded --provider.wallet argument, which means the shell does not tilde-expand it — a plausible oversight in the original Makefile. The justfile's project_deploy_key variable reproduces this exact quoted, non-expanding behavior rather than 'fixing' it, since correcting shell-expansion semantics is out of scope for a mechanical tooling swap.

Execution process and what's still open

The plan describes the six tasks as sequential and independently-committable, but the autonomous loop's default is to spawn every task's worktree agent in parallel from the same base commit — which would break for Task 2 (Docker), since it needs Task 1's pnpm-lock.yaml physically present to verify its build. This was resolved by running three waves instead of one flat parallel batch: Wave 1 = Tasks {1, 3, 4, 5, 6} (verified mutually independent — Task 5's doc content is fully spelled out in the plan, so it doesn't actually need Task 4's justfile to exist on disk to write correct docs), squash-merged; Wave 2 = Task 2 alone (needs Wave 1 merged); Wave 3 = Task 7, a verification-only pass with no worktree since it modifies no files. All 7 tasks passed on the first attempt, and code review round 1 found zero actionable (blocking/important) issues — only four minor items were deferred rather than fixed, none of which block merging.

Challenges & decisions

  • Plan described the 6 tasks as sequential/dependent, but the loop's default worktree spawn is fully parallel — resolved by running 3 waves: Wave 1 = {Task 1, 3, 4, 5, 6} (mutually independent), squash-merged, then Wave 2 = {Task 2} (needed Task 1's pnpm-lock.yaml on disk), then Wave 3 = {Task 7} (verification-only, needed everything merged).
  • Chose `pnpm import` over a fresh `pnpm install` specifically to avoid transitive dependency version drift — verified afterward that all 29 direct dependencies resolved identically, with the only lockfile change being the anticipated postcss-override resolution metadata.
  • The plan's literal stray-reference verification grep false-positived against `pnpm ` (since it contains the substring `npm `); a word-boundary-aware grep was substituted in both Task 5 (docs) and Task 7 (repo-wide sweep).
  • Task 7 checked each chained verification command's exit code individually rather than trusting a single piped `&&` chain, since piping through something like `tail` can mask an earlier command's true exit status.
  • Deliberately preserved a likely-unintentional quirk from the original Makefile — the quoted, non-tilde-expanding `PROJECT_DEPLOY_KEY`/`project_deploy_key` — rather than 'fixing' it, since correcting shell-expansion semantics was judged out of scope for a pure tooling-preference migration.
